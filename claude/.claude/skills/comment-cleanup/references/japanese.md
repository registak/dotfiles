# コメントの日本語

コメントを書き直すとき、短くするときに読む。読み手は、このファイルを初めて開いた別のエンジニアを想定する。

## いちばん大事なこと: 意味を変えない

書き直す前後で、次の5点が同じかを1つずつ比べる。1つでも変わるなら、その書き直しは捨てて元の文を残す。

1. 理由。なぜそうしたかの因果を落とさない。理由が2つあれば2つ残す。
2. 条件と範囲。「本番では」「Meta だけ」「1件も無いとき」のような限定を落とさない。
3. 否定。「しない」「してはいけない」を肯定の言い方にして弱めない。
4. 強さ。「消しうる」を「消す」に、「〜のことがある」を言い切りにしない。逆もしない。
5. 数値、日付、識別子、実測かどうか。`2026-07-31 に本番で実測` のような裏づけは残す。

元のコメントに無い理由、例、数値、一般論は足さない。コードを読んで分かったことでも足さない。
コメントとコードが食い違って見えるときは、直さずに報告する。

短くすることは目的にしない。理由が残っている候補どうしでだけ、短いほうを選ぶ。

## 直すのは、読み手が止まる所だけ

意味の通る文を好みで言い換えない。「〜のため」を「〜ので」にするような、理解の変わらない置き換えはしない。
直すのは次のどれかに当たる所で、当たらない文には触らない。

### 何が起きるのかが動詞から分からない

比喩の動詞や話し言葉は、起きることをそのまま書く。

- 「XFF の内部ホップを掴む」→「XFF の内部ホップの IP をクライアントの IP として使ってしまう」
- 「直列の高速リトライには効く」→「続けて送り直す試行は遅くできる」
- 「黙って leftmost を信頼する」→「警告も出さずに leftmost を信頼する」
- 「ログを吐く」「プロセスが死ぬ」「キューに投げる」→「出力する」「終了する」「渡す」

「キャッシュが効く」のように仕様書でも使う言い方と、「手を打つ」「目を通す」のような慣用句は残す。

### 英語の言い方を1語ずつ置き換えている

英語に訳し戻すと決まった言い方になる句は、日本語でふつうに言う形にする。

- 「日付基準の単一の真実源」→「日付の基準はここだけで決める」
- 「一級市民として扱う」「優雅に劣化する」「端のケース」→ 何をどう扱うかを書く

`single-flight` `upsert` `fail-secure` のような用語は訳さずそのまま使う。「依存性の注入」のように定着した訳語も残す。

### 人でないものを人のように書いている

- 「この関数は呼び出し元の事情を知らない」→「この関数は期間を受け取らない」
- 「DB が嘘をつく」→「DB は再生できると記録したまま、ファイルは壊れている」

「センサーが検知する」のように働きを述べているだけの文と、識別子が主語の文は残す。

### 大げさな名詞で役割を呼んでいる

「主防御」「防波堤」「最後の砦」「契約」「台帳」は、実際にしていることを書く。

- 「書き込み層は防波堤」→「書き込みの直前でも同じ検証をし、変換で漏れた行を弾く」

コードやドキュメントで用語として定義してある語は残す。

### 動作を名詞に詰めて、誰が何をするかが消えている

- 「重複登録の発生の防止」→「同じ広告を二重に登録しない」
- 「未取得判定失敗時」→「未取得かどうかを判定できなかったとき」

「ログイン画面」「取得記録」のように定着した複合語はほどかない。
和語に開きすぎない。「確認」を「確かめ」に、「通知」を「知らせ」にしない。

### 括弧に文や列挙が入っている

括弧の中身は、まず前の文の中に入れる。入らなければ別の文にする。削って困らない言い直しなら削る。

- 「後段(クリエイティブ取得・画像キャッシュ)が失敗しても」→「クリエイティブの取得と画像のキャッシュが失敗しても」
- 「空文字のまま保存する(表示側が「画像なし」に落とす)」→「空文字のまま保存する。表示側が「画像なし」にする。」

残る括弧はコードの記法だけ。`Number("")`、`HMAC-SHA256(key, message)`、`Business Use Case(BUC)` のような略語の定義。

### 中身のない前置きと飾り

- 数の予告と見出しの語: 「重要な前提が3つある。」「注意:」「重要:」「ポイント:」「NOTE:」は外し、中身から書き始める。
  機械や人が検索する `TODO` `FIXME` は残す。
- 強調の語: 「必ず」「絶対に」「非常に」「徹底的に」は、外しても同じことを言えるなら外す。
  「必ず」が条件の一部のときは残す。「必ず失敗するリクエスト」の「必ず」は事実なので残す。
- ダッシュと矢印: 「—」「──」で文をつながない。句点で切るか、接続の語でつなぐ。
  値の変化を示す `300ms → 600ms` は残す。
- 誰も言っていない思い込みの打ち消し: 「〜すればよいわけではない」だけの文は削る。
  「AではなくB」は、A と取り違えやすいときだけ残す。「期間ではなく媒体で絞る」は残す。

## 文の形

- 常体で書き、文として終える。体言止めと「〜ため。」が続いたら、少なくとも1つは述語まで書く。
  定数や型の1行の説明は体言止めのままでよい。
- 1つの文に理由は1つ。「〜ため、〜ので、〜が、」と続く文は分ける。
- 主語と述語を近づける。何が何をするかを省かない。主語が元の文に無ければ、推測で足さない。
- 短い主題の直後に読点を打たない。「この値は、」「更新では、」は「この値は」「更新では」。
  長い節のあと、条件や理由の切れ目、取り違えを防ぐ読点は残す。
- 同じものは同じ語で呼ぶ。コード、近くのコメント、プロジェクトの文書が使っている呼び名にそろえ、
  ファイルの中で言い換えない。新しい呼び名を作らない。
- 識別子、API の名前、値、エラーコードは1字も変えない。
- 英数字と日本語の間の空白、全角と半角は、そのファイルの今の書き方に合わせる。そろえ直さない。

## 書き直したあとの確認

1. 元の文と並べて、冒頭の5点を比べる。
2. その文だけを声に出して読む。同僚に口頭で説明するときの言い方から遠ければ、まだ硬い。
3. 直した所に、新しい比喩、漢語の名詞、括弧、強調の語が入っていないかを見る。書き直しは別の癖を持ち込みやすい。
