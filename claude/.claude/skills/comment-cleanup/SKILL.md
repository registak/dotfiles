# comment-cleanup

規約は `~/.claude/rules/comments.md`。このスキルは、その規約を既存のコードに当てる手順を定める。
コメントを書き直すときの日本語は `references/japanese.md` に従う。1つでも書き直すなら、先に読む。

## 対象範囲

範囲は2通りある。指定が無ければ「差分」で進める。

- 差分: `git diff HEAD` の変更ファイルと未追跡ファイルの中で、追加・変更されたコメントだけを見る。
  コミット前の見直しはこれに当たる。
- 全体: 「ファイル全体」「リポジトリ全体」「既存のコメントも」と言われたときは、指定された範囲のコメントをすべて見る。

対象はソースコードのコメント。`.ts` `.tsx` `.js` `.mjs` `.css` `.sh` `.yml` `Dockerfile` `.env.example` など、
コメントを持つファイルすべて。Markdown の本文は対象外。

## 触らないもの

- コード。空行、インデント、import の順、末尾の改行も含めて1バイトも変えない。
  コメントだけの行を消すときは行ごと消す。行末コメントは直前の空白ごと消す。
- 機械が読むディレクティブ。`eslint-disable*` `@ts-expect-error` `@ts-ignore` `@ts-check`
  `prettier-ignore` `biome-ignore` `istanbul ignore` `c8 ignore` `/// <reference` `turbopackIgnore`
  shebang、ライセンスヘッダ、`.js` の JSDoc の型注釈。ディレクティブと同じコメントに書いた理由も、そのまま残す。
- コメントアウトした設定の見本。`.env.example` の `# KEY=value` は読み手が写して使うので、行を消さない。
- `// --- 見出し ---` の形の区切り。行ごと消すと前後の空行が2つ続き、空行を変えないという制約とぶつかる。
  見出しの語を直すことはしてよい。
- 分かりにくいコードをコメントが補っている所。コメントは残し、リファクタの候補として報告する。

## 判定

コメントを1つずつ、次の順に当てはめ、最初に当たった区分で処理する。

1. コードの逐語説明。処理の手順、名前・型・シグネチャの繰り返し、ブロックの終わりの印。削除する。
2. 差分の説明。「〜に修正」「〜を追加」「以前は〜していた」のように、diff を見ていない人には意味が通らないもの。
   削除し、コミットメッセージへ移す内容として報告する。
   ただし以前の実装で起きた失敗が今の書き方の理由になっているなら、経緯を外して理由だけを残す。
3. 消えると読めなくなる参照。仕様書の節番号や設計ドキュメントへのリンクに頼っているもの。
   参照を外し、内容だけで読める文にする。チケット ID、RFC、安定したパスの README や ADR は道しるべとして残してよい。
4. 長すぎる理由。本物の理由を持つが長い。5行以上のブロックはまず疑う。理由を落とさずに短くする。
5. コードと合っていないもの。存在しない名前や、変わった挙動を指している。削除する。
   警告の性質を持ち、真偽を判断できないなら、残して報告する。
6. 残す。コードから読めない理由。外部仕様の制約、意図的な逸脱、罠、互換性のための回避策、
   単純な書き方を避けた理由、実測で分かった事実。公開関数とエンドポイントの1行の説明。
   テストの期待値がどう導かれるかを示すコメントも、コードから読めないので残す。

### 迷ったら残す

本物の警告を消したときの損は、余計なコメントを1行残したときの損より大きい。
理由かどうかで迷ったら残す。迷わず消してよいのは 1 と 2 だけ。

短くするときにいちばん起きやすい失敗は、理由が2つあるコメントから1つを落とすことである。
短くしたコメントは、元の文の理由・条件・否定・強さ・数値を数え、同じ数だけ残っているかを確かめる。

## 残すコメントの日本語

全体を見るときは、残すと決めたコメントも `references/japanese.md` に照らして読む。
差分を見るときは、追加・変更されたコメントに同じことをする。

直すのは読み手が止まる所だけにする。比喩の動詞、英語の直訳、擬人化、大げさな名詞、
名詞に詰めた動作、文の入った括弧、中身のない前置き、がそれに当たる。
意味の通る文を好みで言い換えない。全部を同じ調子に書き直すと、それ自体が機械の書いた文章に見える。

## 手順

1. 対象のコメントを並べる。全体を見るときは次のコマンドで行番号つきの一覧にできる。

   ```
   node <このスキルのディレクトリ>/scripts/check-comment-only.mjs --list <パス...>
   ```

2. 「判定」の順に1つずつ処理する。sed や一括の置換は使わない。同じ形のコメントが並んでいても、
   前後のコードを読んで1つずつ決める。
3. 書き直したコメントを、元の文と並べて読み比べる。
4. コメント以外が変わっていないことを機械で確かめる。対象のリポジトリの直下で実行する。

   ```
   node <このスキルのディレクトリ>/scripts/check-comment-only.mjs [--base <ref>] [パス...]
   ```

   TypeScript と JavaScript は構文を解析してコメントを抜き、残りが1文字も違わないことと、
   ディレクティブが変わっていないことを見る。CSS と、`#` で始まる行のコメントを持つファイルにも対応する。
   行末の `#` と、対応していない形式のファイルは差分を目で確かめる。
   NG が出たら、その箇所を戻すか直す。スクリプトを通すためにコードを動かさない。
5. テスト、型チェック、lint があれば実行する。
6. 報告する。

## 範囲が広いとき

数十ファイルを超えるなら、ディレクトリや層で分けてサブエージェントに渡し、自分は司令塔になる。

- エージェントには、このファイルと `references/japanese.md` と規約を読ませ、担当のファイルの一覧を渡す。
- エージェントは自分の worktree で作業し、検査スクリプトを通してから、`git diff` をパッチとして書き出す。
- 司令塔はパッチを全部読む。削除と短縮で理由が落ちていないかを見て、落ちていれば自分で戻す。
  読まずに当てない。
- PR は層ごとに分け、1本の差分を人が読み切れる大きさにする。

## 報告

- 区分ごとの件数
- 理由を持つコメントを短くした・書き直した所で、意味が動きやすいものの前後を `ファイル:行` つきで
- コードと食い違って見えたコメント
- 残したが迷ったコメント
- リファクタの候補
- コミットメッセージへ移す内容
- 検査スクリプトとテストの結果
