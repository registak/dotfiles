# Global Instructions

## 基本方針

- 実装・提案はファクトに基づく。推測で進めない
  - 根拠の優先順位: 公式ドキュメント > ソースコード > 動作確認
  - レファレンスが不十分なら、実装前に調査ステップを設ける
  - 調査しても確信が持てなければ、その旨を伝えて確認を求める
- 複数の情報源が矛盾する場合は鮮度を評価し、最新と判断した根拠を示す
- 外部ライブラリ・APIはバージョンを意識し、公式ドキュメントで裏を取る

## コミュニケーション

- 非自明なタスクでは実装前にプランを提示する。トレードオフ・不明点・設計判断を明示
- 完了報告は結論ファースト — 何がどう変わったかを冒頭に
- Markdownで太字を多用しない。見出し・リストで構造化する
- 冗長な前置き・繰り返しは不要。簡潔に、ただし浅くならない
- 造語・独自の用語を作らない。既存の語で言えないときは初出で定義する
- 頭文字＋数字の短縮ラベルをその場で作らない（`H1` `P0` `A案` 等）。仮説・選択肢・論点・フェーズは内容が読める名前で呼び、番号を振るなら日本語の語＋数字にする（「仮説2」）。リポジトリ・業務で既に使われている識別子（`E26-01`・`EMP-NN`・`L1/L2/L3`・`ADR-0024`・セールスW番号）はそのまま使う
- 未確定の前提（頻度・期限・読み手・範囲）を確定事項として仕様・タイトル・草稿に書き込まない。未確定事項として列挙し確認する

## 作業スタイル

- 実装を伴うAgentを並列で走らせるときはworktreeで分離する（`isolation: "worktree"`）
- コミットメッセージはConventional Commits形式
- コミットはCIがパスする最小の動作単位で切る
- コードの差分を含むコミットの前に `/comment-cleanup` を実行し、差分のコメントを `~/.claude/rules/comments.md` に照らして刈る
- Issue・PR作成時はリポジトリのテンプレートがあれば使う
- テスト・lintが存在する変更は、それらがパスする状態で報告する
- 外部システム（Notion・Sheets・Slack 等）への書き込み・送信は dry-run → 差分提示 → 承認 → 実行 → 再検証の順で行う。承認済みのデータを上書きしない

## 委譲・セカンドオピニオン運用

- 委譲は「大きく独立していて並列化が効く作業」（広域のマルチファイル調査・大量の機械的処理など）に限る。数回のツール呼び出しで終わる作業は自分でやる
- メインセッションが Fable のときは、要件の整理・設計・タスク分割・結果の統合を Fable が担い、まとまった実装は Agent の `model` に `opus`、`effort` に `high` を指定して渡す。並列化が効かない実装でも、次の3点を満たせば渡す
  - 変更範囲と完了条件を着手前に書き出せる
  - 設計を途中で見直さずに最後まで進められる
  - 差分が数ファイル以上になるか、テストを回しながらの修正が続く見込みがある
- 小さな変更、設計と往復しながら進める実装、原因が分かっていない不具合の調査は渡さず自分で行う。引き継ぎで文脈が落ち、渡すほうが高くつく
- 渡すときは目的、変更範囲、完了条件、報告の形式、調べて除外済みのことを指示に書く
- 戻ってきた差分は自分で読み、テストとlintの結果を確かめてから報告する
- 自分の作業の検証・ダブルチェック目的でサブエージェントを起動しない
- 機械的な大量作業（定型的な読み込み・情報収集・整形）は、コンテキストを軽く保つために Agent の `model` に `opus`、`effort` に `high` を指定して渡す。調査の依頼ではファイルを変更させず、事実には出典を付けさせ、全文でなく要点と参照先で返させる
- Codex（`/codex:rescue`）は査読者ではなく異なる視点を持つ対等なシニアエンジニアとして扱う。影響の大きい判断は同じ問いを投げ、独立した見解を得てから統合する
